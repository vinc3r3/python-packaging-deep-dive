# 03 - site-packages

This chapter explains what `site-packages` actually is and why it matters so much.

If chapter 1 gave us the runtime model and chapter 2 explained how `venv` redirects Python into a private environment, this chapter answers the next practical question:

> where do installed packages physically live, and how does Python discover them?

That matters because many packaging problems only become understandable once you can connect three different layers:

- the package manager's view of an installed distribution
- the filesystem layout inside `site-packages`
- Python's import system at runtime

---

# 1. The short version

`site-packages` is the main directory where third-party Python packages are installed.

It is usually added to `sys.path` during interpreter startup, which makes its contents importable.

Inside it, you will commonly find:

- Python packages and modules
- compiled extension modules such as `.so` or `.pyd`
- metadata directories such as `.dist-info`
- `.pth` files that can extend import paths
- console-script entry point wrappers

If you understand what lives in `site-packages`, you understand what `pip install` actually changes.

---

# 2. Why this directory matters

When people say "I installed a package," they often imagine one simple action.

In reality, installation usually means:

- files were written into `site-packages`
- metadata was recorded
- Python startup may now see new import paths
- shell command wrappers may have been created

So `site-packages` is not just "a folder with libraries."

It is the main boundary between:

- package distribution tooling
- import-time behavior
- environment-local state

---

# 3. Where `site-packages` lives

In a typical environment, the path looks roughly like:

```text
.../lib/pythonX.Y/site-packages/
```

On Windows, the layout differs slightly, but the idea is the same.

Inside a virtual environment, it usually lives under the venv root:

```text
.venv/lib/pythonX.Y/site-packages/
```

You can inspect it directly:

```python
import site
print(site.getsitepackages())
```

In some cases, especially across platforms and interpreter builds, there may be more than one relevant package location.

---

# 4. How `site-packages` becomes importable

`site-packages` matters because Python typically adds it to `sys.path` during startup.

That means anything placed there becomes visible to the import system.

You can verify this:

```python
import sys
for p in sys.path:
    print(p)
```

Some of those entries will usually point to:

- standard library directories
- the current project directory
- one or more `site-packages` directories

This leads to an important mental model:

> `site-packages` does not have special magic by itself. It matters because it is placed on `sys.path`.

---

# 5. What you typically find inside

A real `site-packages` directory may contain several different kinds of things.

For example:

```text
site-packages/
├── requests/
├── requests-2.32.0.dist-info/
├── numpy/
├── numpy.libs/
├── myproject.pth
└── pip/
```

The important categories are:

- importable package directories such as `requests/`
- standalone modules such as `foo.py`
- metadata directories such as `requests-2.32.0.dist-info/`
- compiled binaries used by extension modules
- path configuration files such as `.pth`

This mix is one reason packaging can feel confusing: not everything in `site-packages` is there for the same purpose.

---

# 6. Distribution name vs import name

One beginner pain point is assuming the package name on PyPI is always the same as the name you import.

That is not guaranteed.

Examples:

- you install `beautifulsoup4`
- you import `bs4`

Or:

- you install `Pillow`
- you import `PIL`

This happens because packaging has two related but different concepts:

- distribution name: the thing installers and indexes track
- import package name: the module or package Python loads at runtime

That distinction becomes visible inside `site-packages`:

- the metadata directory reflects the distribution
- the importable package directory reflects the import name

This is a very useful debugging insight when "installed" and "importable" seem out of sync.

---

# 7. `.dist-info` is the installer's memory

When a modern package is installed, you will usually see a directory like:

```text
requests-2.32.0.dist-info/
```

This is not the package code itself.

It is metadata about the installed distribution.

It commonly contains files such as:

- `METADATA`
- `RECORD`
- `WHEEL`
- `entry_points.txt`

Conceptually:

- `METADATA` describes the distribution and its dependencies
- `RECORD` lists installed files
- `WHEEL` describes wheel-specific installation details
- `entry_points.txt` can define generated command-line scripts

This metadata is part of how tools know:

- what version is installed
- what files belong to that install
- which console scripts to create
- how uninstall should work

Without `.dist-info`, modern packaging tools would have a much weaker memory of the installation.

---

# 8. Package code vs metadata

It helps to separate two questions:

1. What does Python import?
2. What does the packaging tool know was installed?

Python mostly cares about importable files on `sys.path`, such as:

- package directories
- module files
- extension modules

Packaging tools care about those files too, but they also care about metadata, versioning, dependency declarations, and uninstall tracking.

That is why a normal installation has both:

- package code
- `.dist-info` metadata

The code serves runtime.
The metadata serves tooling.

---

# 9. `.pth` files can silently change imports

One of the most important hidden mechanisms in `site-packages` is the `.pth` file.

A `.pth` file can add extra directories to `sys.path` during startup.

Example:

```text
myproject.pth
```

containing:

```text
/Users/me/src/myproject
```

That means Python may import from that source tree even though the code is not physically copied into `site-packages`.

This is one reason imports can feel mysterious:

- the package is not visibly "installed" in the obvious way
- yet Python can still import it

This mechanism is especially important for editable installs.

---

# 10. Editable installs, revisited

When you run:

```bash
python -m pip install -e .
```

your source tree often remains where it already is.

Instead of copying code into `site-packages`, packaging tooling usually makes your project directory importable from the environment.

That may happen through:

- a `.pth` file
- a link-like mechanism
- backend-specific editable install support

The practical effect is:

> Python imports your package from the working source tree, not from a copied snapshot

This is great for development because edits show up immediately.

It also means your environment can depend on the current state of your checkout, which is very different from a regular installed wheel.

---

# 11. Console scripts also come from installation

When you install some packages, new commands appear in your environment:

```bash
pytest
uvicorn
jupyter
```

These commands are usually small wrapper scripts created during installation.

They are not the package itself.

They are entry points that say, in effect:

- import a specific function
- execute it as a command-line program

Those generated scripts typically live in:

- `.venv/bin/` on Unix-like systems
- `.venv/Scripts/` on Windows

So installation does not only affect imports. It also changes the executable tools available in the environment.

---

# 12. Native extensions live here too

Not everything in `site-packages` is pure Python.

Many important packages include compiled extensions, such as:

- `.so` files on Linux and macOS
- `.pyd` files on Windows

Examples include parts of:

- `numpy`
- `pandas`
- `torch`
- many tokenizer, vision, and scientific libraries

This matters because installation is not always "copy some `.py` files."

Sometimes it also means placing prebuilt native binaries in locations where Python can import them.

That is one of the main reasons wheels exist and why compatibility becomes such a big topic later.

---

# 13. Why `site-packages` can become messy

Real environments accumulate complexity over time.

Common sources of confusion include:

- old versions left behind after repeated installs
- editable installs mixed with regular installs
- leaked paths from `.pth` files
- user-site packages interacting with venv packages
- distribution names that do not match import names

From the outside, all of these can look like:

- "Python imported the wrong thing"
- "I uninstalled it but it is still there"
- "This package is installed but import still fails"

Those are often `site-packages` layout problems, not abstract packaging mysteries.

---

# 14. A practical inspection workflow

When you want to understand what is really installed, inspect the environment directly.

Start from Python:

```python
import site
import sys

print("site-packages:", site.getsitepackages())
print("sys.path:")
for p in sys.path:
    print(" ", p)
```

Then inspect the directory itself from the shell:

```bash
ls .venv/lib/python3.11/site-packages
```

And if you want to inspect package metadata:

```bash
python -m pip show requests
```

These checks help answer:

- where a package was installed
- whether it is in the active environment
- whether Python can actually see that location

---

# 15. Key mental model

`site-packages` is best understood as:

```text
[ importable code ]
        +
[ installation metadata ]
        +
[ optional path injections and generated scripts ]
```

It is the place where package management and Python runtime behavior meet.

---

# 16. What this chapter should give you

After this chapter, the useful takeaway is not just "packages live in `site-packages`."

The more valuable takeaway is:

- installation is a filesystem event
- importability depends on `sys.path`
- metadata and code are related but not identical
- editable installs often work by path redirection, not code copying

Once you see that clearly, a lot of packaging behavior stops feeling magical.
